# 产品需求与设计

> 题目原文要求 "**了解开发者在代码评审中的真实需求**,设计并实现一个以 AI 辅助分析为核心的工具"。
> 本文是这部分的产品调研与设计落地。

## 一、用户画像

我们把目标用户分成两类,产品功能优先服务**主用户**,顺便覆盖**辅用户**:

### 主用户:Reviewer(代码评审员)
- 角色:中高级工程师 / Tech Lead / 模块 Owner
- 评审频率:平均每周 5-15 个 PR
- 痛点最强烈:**注意力分配**(哪个 PR 该认真看 / 哪个扫一眼即可)
- 核心需求:让 AI 帮我**先过一遍**,标出可能的真问题,我再决定深入哪些

### 辅用户:Author(PR 作者)
- 角色:刚提交 PR,等待 reviewer 回复
- 心理:希望 PR 顺利通过,提前自查可能的问题
- 核心需求:**自助式预审**,提交前自己先看一遍,把低级问题改掉再发出去

## 二、真实需求清单(及本工具如何回应)

下表是从开发者社区(GitHub / Reddit / 国内技术博客 / Code Review 类工具的 issue tracker)提炼出的高频痛点。每一项都对应到本工具的具体设计决策。

### 痛点 1:大 PR 看不动,关键问题被淹没

> "200 行的 PR 我能仔细看,800 行的 PR 我只能扫一眼,然后 LGTM。"

**本工具的应对**:
- **三层 prompt 策略**:粗筛阶段先判定每个文件是否值得深审(deep / normal / skip),lockfile / 大段格式化 / 自动生成代码自动跳过
- **风险按 severity 排序**:high 级别的真 bug 排在最前,reviewer 看头几条就够了
- **置信度过滤**:低 confidence 的建议折叠到次要区域,不让 reviewer 被噪音淹没

### 痛点 2:误报多,信任度难建立

> "AI 给的建议十条里九条是废话,看完我没节省时间反而花了更多时间。"

**本工具的应对**:
- **跨文件上下文**:模型不只看 diff,还看改动文件的完整内容,大幅降低"这变量在别处其实是这么用的"型误报
- **prompt 强约束**:system prompt 明确"忠于事实,只对 diff 中实际出现的代码发表意见;关注真正影响正确性的问题;每条带置信度",降低空泛建议
- **置信度三级**:high/medium/low,reviewer 可只看 high 节省时间
- **依据引用**:每条 risk 必须带 file + line_hint,reviewer 可立即定位验证

### 痛点 3:看完 diff,我还得自己写 review comment

> "我已经花了 20 分钟读懂这个 PR,然后还要花 10 分钟把发现的问题敲成评论..."

**本工具的应对**:
- **复制为 Markdown 按钮**:评审完成后一键复制成 markdown,可直接粘贴到 GitHub PR 评论区
- 输出结构本身就是 review comment 友好的:每条 risk 是一段独立 markdown,带 \`severity / category / file / line\` 元信息

### 痛点 4:Reviewer 给的反馈风格不一致

> "Alice review 抓代码风格,Bob review 抓性能,Carol review 抓安全 — 但他们都不在的时候 PR 就裸奔。"

**本工具的应对**(部分实现 + 扩展点):
- **当前**:system prompt 同时关注 \`bug / perf / security / style / other\` 五大类,每条 risk 标记 category
- **未来扩展**:支持团队上传"代码规范文档"(\`style_guide\` 字段),让评审按团队风格来。详见 [docs/extending.md § 加入团队规范的个性化评审](./extending.md#加入团队规范的个性化评审)

### 痛点 5:重复看同一个 PR 浪费时间和 token

> "PR 改了 3 次,每次 reviewer 都得重新过一遍。"

**本工具的应对**:
- **commit SHA 级缓存**:同一 PR 同一 commit 第二次评审 0 秒返回,代码无变化直接给上次结果
- **\`force_refresh: true\` 参数**:确实想重跑也支持

### 痛点 6:不知道工具花了多少 LLM token

> "我用 ChatGPT review PR,一个月烧了 50 美元才发现。"

**本工具的应对**:
- **token 透明**:每份评审报告都附 \`prompt_tokens / completion_tokens / total_tokens / llm_calls\`
- 前端在完成行下显示:\`4 次 LLM 调用 · 3,224 prompt + 4,920 completion = 8,144 tokens\`
- 缓存命中的请求不计费(\`elapsed_ms < 100ms\` 是最直观的"免费"标识)

### 痛点 7:LLM 偶尔挂掉,工具就废了

> "上次评审到一半,Claude 服务挂了,我整个工作流卡住。"

**本工具的应对**:
- **模型 fallback 链**:\`primary → fallback\` 双轨,任意主路抖动自动切兜底,不中断评审
- **JSON 解析容错**:LLM 偶尔输出含智能引号 / 控制字符的非法 JSON,加 \`_clean_json_like\` 二次容错,降低"模型抽风导致 500"的概率
- **错误响应给中文 hint**:\`LLM 网关暂时不可用,请稍后重试。这通常是上游模型服务的瞬时抖动\`

### 痛点 8:Demo 时网络抖,评审一直等

> "向同事演示 AI Review 工具,粘 URL 之后等 90 秒还在转圈,场面尴尬。"

**本工具的应对**:
- **SSE 流式渲染**:5-15s 看到 PR 总览,30-60s 内陆续看到风险卡片,**用户始终看到进度**
- **缓存命中**:演示前先评审一次,演示时缓存命中瞬时返回,作为"备选演示路径"

## 三、产品设计原则

基于上面 8 个痛点,我们提炼出 4 条贯穿全产品的设计原则:

| 原则 | 体现 |
|---|---|
| **降噪优先于求全** | 三层 prompt 跳过 lockfile;低 confidence 折叠;每条 risk 必须带 hint |
| **过程透明** | SSE 流式 + token 用量 + 模型名,reviewer 知道工具在干什么、花了多少 |
| **可立即采纳** | 输出是 markdown,可一键复制粘贴;每条带 file + line + 修改方向 |
| **绝不卡死** | fallback 链、错误统一格式、缓存命中、流式心跳 |

## 四、为什么选「PR 评审」这个切入点

题目给了三个选项,我们选 PR Review 助手而不是语音日历或多平台发布,理由:

1. **资源匹配**:文本 + 代码理解,我们的 LLM 网关刚好覆盖(deepseek / claude),不需要语音 ASR/TTS、不需要图像生成
2. **真实痛点**:大型团队 PR 评审瓶颈是真实问题,不是凭空想象的需求
3. **工具地位**:Claude Code 自身就是 reviewer 工具的代表,评委会用同类思维评判
4. **演示效果好**:粘任意公开 PR URL 即可现场演示,不依赖任何账号 / 数据准备
5. **延展空间大**:从 PR 评审 → GitHub App → 自动化 CI Gate,有清晰的产品路线

## 五、与同类产品的差异

我们调研过这些同类工具:

| 工具 | 我们的差异 |
|---|---|
| GitHub Copilot Code Review | 闭源、贵、不可定制;**我们开源,且接 OpenAI 兼容协议任选模型** |
| CodeRabbit | 企业向、付费;**我们个人/小团队友好,Docker 一行启动** |
| Greptile | SaaS,数据要上云;**我们自托管,代码不出私网** |
| 手写 ChatGPT prompt | 只看 diff;**我们看 diff + 全文,大幅降误报** |

我们不是要做企业级"完美"产品,而是要做一个 **"周末用 LLM 工具帮自己 review PR"** 的开发者最舒服的工具。
