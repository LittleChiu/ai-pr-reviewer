# Demo 视频脚本

> 目标:用 3-5 分钟讲清楚产品做了什么、有什么差异、为什么这么设计。

## 一、视频结构(总长 4-5 分钟)

```
0:00 - 0:30  开场:产品定位与价值主张
0:30 - 1:30  核心功能演示:粘 PR URL → 流式评审
1:30 - 2:30  差异化亮点:三层 prompt + 跨文件上下文 + 缓存
2:30 - 3:30  真实 PR 评审 showcase(httpx#3670)
3:30 - 4:00  技术架构与模型策略
4:00 - 4:30  扩展方向与收尾
```

## 二、详细分镜与文案

### 镜头 1:开场(0:00 - 0:30)

**画面**:首页空态(柔和渐变背景 + logo + 输入框)

**口播**:
> 大家好,这是 AI PR Review,一个智能代码评审助手。
> 它的目标很简单:把人工 review 一个大型 PR 需要 30 分钟的工作,
> 压缩到 30 秒内拿到一份带置信度的智能评审报告。
> 不是替代 reviewer,而是给 reviewer 一个高于平均水平的'第二双眼睛'。

**操作**:鼠标悬停在输入框上,展示提示文字

---

### 镜头 2:核心功能演示(0:30 - 1:30)

**画面**:粘贴 PR URL,提交,流式渲染过程

**操作**:
1. 在输入框粘贴 `https://github.com/encode/httpx/pull/3670`
2. 点击「开始评审」
3. **5-15 秒后**:总览 + 亮点出现
4. 文件深审进度条:每个文件的圆点从灰→蓝(running)→绿(done)
5. **30-90 秒**:风险卡片陆续出现,带 severity 色条

**口播**(配合画面节奏):
> 我们粘贴一个真实的开源 PR 链接 — 这是 encode/httpx 的一次重构。
> 提交以后...看,几秒钟内 PR 总览就到了 — 这是三层 prompt 策略里的'粗筛'阶段。
> 接下来是文件深审,你能看到每个文件的进度实时更新...
> 风险报告陆续出现,左侧色条标识严重程度:红色 high、橙色 medium、灰色 low。
> 每条风险都带文件路径、行号、置信度。
> 这就是产品的核心交付:**结构化、带证据、可立即采纳**。

---

### 镜头 3:差异化亮点(1:30 - 2:30)

**画面**:边讲边鼠标指向页面元素

#### 3.1 三层 prompt(0:30s)

> 为什么不是一次性把整个 diff 喂给 GPT?
> 因为那样模型既要做'分类'又要做'深度推理',效果会打折。
>
> 我们做了三层:
> - 第一层用 fast 模型(deepseek-v4-flash)做粗筛,判断每个文件值不值得深审
> - 第二层用强模型(deepseek-v4-pro-max)逐文件深审,带上**完整文件内容**,不只是 diff
> - 第三层做聚合,按严重程度排序

#### 3.2 跨文件上下文(0:20s)

> 关键差异化:**模型看的不只是 diff,还有改动文件的完整内容**。
> 这意味着模型能理解'这个变量在别处是怎么用的',大幅降低误报率。
> 而通用 ChatGPT prompt 看 diff,误报很多就是因为缺这个上下文。

#### 3.3 缓存演示(0:30s)

**画面**:评审完成后,**再粘一次同一个 URL**,几乎立刻出结果

> 同一个 PR 评审完后,结果会按 commit SHA 缓存。
> 看,**第二次粘同一个 URL,瞬时返回**。
> 这对'反复看同一个 PR 的 reviewer 工作流'非常友好,也节省 token。

---

### 镜头 4:真实 PR Showcase(2:30 - 3:30)

**画面**:打开 docs/showcases/showcase-c-encode-httpx-3670.md(GitHub 上)

**口播**:
> 我们对 3 个真实公开仓库的 PR 跑了评审,结果都在 docs/showcases/ 里。
>
> 比如这个 httpx#3670,模型抓到一个 high 级别的真 bug:
> '对同步文件对象用 await self._fin.close() 会抛 TypeError'。
> 这是个**人类 reviewer 也容易漏的真实问题**,
> 模型不仅指出了行号,还给了具体修改方向。
>
> 另外两条 medium 级别的发现也很有价值:
> os.path.getsize 重复系统调用、FileStream 签名变更破坏调用方契约。
>
> 这就是工具的实战价值 — 不是堆砌建议,是真的能帮 reviewer 抓 bug。

---

### 镜头 5:技术架构(3:30 - 4:00)

**画面**:打开 docs/architecture.md 上的 ASCII 架构图

**口播**:
> 简单介绍下技术栈:
> - 前端 Next.js 16,SSE 流式渲染,~30 行代码自手动解析 SSE,不引重型库
> - 后端 FastAPI + uv,异步并发深审,asyncio.Semaphore 限并发
> - LLM 网关用 OpenAI 兼容协议,支持 fallback 链 — 主路挂了自动切兜底
> - SQLite 缓存,标准库 sqlite3 直接用,不引 ORM
>
> 设计原则就一条:**KISS**。能用标准库不引第三方,能 ~30 行解决不引整个库。

---

### 镜头 6:扩展方向与收尾(4:00 - 4:30)

**画面**:回到首页或显示 README 的"未来扩展方向"

**口播**:
> 未来扩展也很清晰:
> - GitHub App 集成,PR 创建即自动评审,以 review comment 形式回写
> - 类型推断辅助 / 依赖图感知 / 仓库历史 review 风格学习
> - 视觉模型激活,理解 PR 描述里的架构图截图
>
> 这个工具我们用 72 小时做出来,代码完全开源。
> 谢谢观看。

## 三、录制注意事项

### 环境准备
- [ ] 浏览器:Chrome / Edge,1280x800 窗口大小,关闭其它无关 tab
- [ ] 后端服务已起,且**预先评审过 demo 用的 PR**(让缓存命中,避免视频里等 LLM 太久)
  - 或者展示流式过程时**不要用缓存**,展示真实的 30-90 秒等待
- [ ] 前端 `pnpm build && pnpm start` 用生产模式(更快、不出现 dev banner)
- [ ] 关闭浏览器扩展(避免页面元素干扰)

### 录制软件
- macOS:QuickTime / OBS Studio
- Windows:OBS Studio / Win+G
- Linux:OBS Studio
- 最低分辨率:1080p(1920x1080),建议 30fps

### 后期处理
- 剪掉不必要的等待(LLM 响应那 60s 可以加速 4x)
- 关键元素加箭头/方框标注(severity 色条、置信度标签等)
- 可选:加字幕(中英文)

### 上传
- B 站(国内观众首选)
- 公开 / 不限制评论 / 不带广告
- README 里加视频链接
